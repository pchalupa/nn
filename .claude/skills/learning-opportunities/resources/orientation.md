# Repo Orientation: nn

> Generated by orient. Re-run to update.

## One-line purpose

`nn` is a local-first state management library for TypeScript: you describe app state with a schema, a store keeps it in CRDTs so edits made offline, in other tabs or on other devices merge automatically, and pluggable sync engines connect that store to IndexedDB, other tabs or a server.

## Primary language(s)

- TypeScript (pnpm workspace, Node >= 24, built with tsdown, tested with Vitest, linted with oxlint/oxfmt)
- LaTeX (the thesis and assignment under `docs/thesis` and `docs/assignment`, not part of the library)

## Pipeline / workflow stages

1. **Schema**: the app declares state with builders from `@nn/schema` (`object`, `array`, `string`, `number`, `boolean`, `enumeration`).
2. **Strategy tree**: `new Store(schema)` calls `createReconciliationStrategy`, which maps each schema node to a strategy (object → `MapStrategy`, array → `ListStrategy`, scalar/enum → `RegisterStrategy`).
3. **Entity tree**: strategies create CRDT entities (`LWWMap`, `RGA`, `LWWRegister`) under a root `LWWMap` keyed `"state"`, stamped with `Time.epoch()` so any real write wins.
4. **Read**: `store.query(selector)` reads through `View`, which materializes frozen plain objects and caches them per entity `revision`.
5. **Write**: `store.mutate(recipe)` hands the recipe a `Draft` (proxy trackers), then the strategy tree reconciles the edited draft back onto the entities, so only touched fields change.
6. **Commit and notify**: `Store.commit` collects changed root fields through the entity delegate and notifies `onChange` listeners with lazily encoded entries.
7. **Sync out**: each `SyncEngine` subscribed to `onChange` calls its transport's `push(name, entry)`.
8. **Sync in**: engines `pull` on connect or `receive` pushed records, then call `store.merge(name, encoded)`, which decodes, `conform`s to the schema and CRDT-merges into the local entity.
9. **UI**: `@nn/react`'s `createStore` wraps the store in `useQuery` (via `useSyncExternalStoreWithSelector`) and `useMutation`.

## Core concepts

**CRDT entities**: Conflict-free replicated data types that hold the state. `LWWRegister` (one value, last writer wins by timestamp), `LWWMap` (object fields), `RGA` (ordered list with tombstoned removals, see ADR-03 and ADR-19). Live in `packages/entities/src/`; `codec.ts` / `codable.ts` encode them as `{ key, data, metadata: { kind, ... } }`.

**Reconciliation strategies**: The bridge from "plain JS value the user edited" to "CRDT operations". Each strategy knows how to `create` an entity, `reconcile` a draft value into it, and `conform` a decoded remote entity to the local schema. Live in `packages/store/src/reconciliation/`.

**Projections (View and Draft)**: `View` turns entities into frozen, cached, schema-shaped snapshots for reads; `Draft` gives `mutate` recipes a lazily-filled mutable proxy and tracks what was touched so reconciliation skips untouched subtrees. Live in `packages/store/src/projections/` (trackers in `projections/tracker/`).

**Hybrid logical clock**: `Time` combines wall-clock ms, a counter and a replica id into a totally ordered timestamp so concurrent writes from different replicas resolve deterministically. Lives in `packages/time/src/time.ts`; clock state is static and process-wide.

**Sync engines with a session lifecycle**: Persistence and networking attach from outside the store (ADR-13). `SyncEngine` owns ordering and error rules; a `Session` state machine (`idle → connecting → connected → disconnected → disposed`) drives it. Subclasses supply only `open`, `close`, `push` and optionally `pull`. Live in `packages/sync-engine/src/` plus one package per transport.

## Common gotchas

- **Generated `exports` and subpath imports.** Imports like `@nn/entities/kinds/lww-map` resolve to `packages/entities/src/lww-map.ts` through the `exports` map in `package.json`, which is generated from the entries in `packages/entities/tsdown.config.ts`. To add or rename an entry point, edit `tsdown.config.ts` and run `pnpm build`; don't hand-edit `exports`. In the workspace everything runs from `src/*.ts`, and only `pnpm pack`/`pnpm publish` swap in `publishConfig.exports` (so never `npm publish`).
- **Stale names in the docs.** Removed packages such as `@nn/repository`, `@nn/repository-sync` and `@nn/http-remote` still appear in old ADRs and in the untracked `coverage/` report. ADRs in `docs/decisions/` describe history: ADR-13 says `store.changes`/`store.updates` and `RepositorySync.attach`, but its "Amended by" lines point to ADR-14/16/18, which replaced those with `store.onChange`, `new XSync(store, ...)` and `connect()`. Always check the "Amended by" header and the current source before trusting an ADR.
- **Keys and timestamps decide merges.** Map fields are keyed by their field name (and the root by `"state"`), so the same field on two replicas lines up; list items get fresh `ID.create()` keys, so a spread or copied item is a _new_ item (see the "identity" tests in `packages/store/src/store.test.ts`). `Store.merge` silently ignores a remote entry whose `key` doesn't match the local entity, and defaults are stamped with `Time.epoch()` so that any real remote write beats them. Repo rules also forbid `as` casts and `any` (the two `oxlint-disable` TODOs in `store.ts` are known debt, not a pattern to copy).

## Suggested exercise sequence

1. **How an app assembles the stack.** Open `examples/react/src/store.ts` (22 lines) and read it top to bottom. Then explain in your own words: what each of the three sync engines (`IndexDbSync`, `BroadcastSync`, `SseSync`) is responsible for, why they're created separately from the store instead of being passed into it, and why the file calls `remote.retry()` on the `online` and `visibilitychange` events. If an engine's role is unclear, the package `description` fields in `packages/*/package.json` are a one-line hint.

2. **From schema to CRDTs.** Open `packages/store/src/reconciliation/create-strategy.ts` (46 lines) and read the bottom implementation of `createReconciliationStrategy`. Then open `examples/schema/src/index.ts` and pick the exported `schema`. Describe the tree of strategies, and therefore CRDT kinds, that the store would build for it: what backs `tickets`, what backs one ticket's `status`, and what backs `language`. Finish by saying in one sentence why a schema is required up front for this design to work.
